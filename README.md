# Dogui Mart Pro SaaS

Gestion de commerce **pour Android** : PWA installable (TanStack Router/Query + React 19 + Tailwind 4) sur **Appwrite** (Auth, Teams, TablesDB). Inspiré des modules d'Odoo (POS, stock, achats, compta) et de Dolibarr (tiers, factures), adapté au petit commerce africain (FCFA, Mobile Money, SYSCOHADA, hors-ligne).

## Démarrage
Backend : projet Appwrite **PRO HRI CENTER** (`6ae9d6010001952ea399`, Francfort). La base `dmp` et ses 12 tables existent déjà.
```bash
npm install
cp .env.example .env
npm run dev
```
### Déployer la fonction serveur (à faire une fois, avec votre compte)
La fonction `dmp-api` est déjà créée dans le projet, mais **son code n'est pas encore déployé**.
```bash
npm i -g appwrite-cli && appwrite login
npm run functions:build        # produit functions/dmp-api/dist/main.js
appwrite push functions        # lit appwrite.json
```
Puis dans la console Appwrite : *Overview → Platforms → Add Web app* avec le domaine de l'application (nécessaire pour que le navigateur puisse appeler Appwrite).
Contrôles : `npm run typecheck && npm test && npm run build`.

## Architecture
- **Multi-tenant** : un commerçant = une *Team* Appwrite (rôles `owner` / `manager` / `cashier` / `stockkeeper` / `accountant`). Chaque ligne porte `tenantId` + `shopId` et des droits de ligne basés sur la Team (`rowPerms`).
- **Domaine pur et testé** (`src/domain`) : montants FCFA, encaissement, fidélité, crédit client, stock par mouvements immuables, écritures SYSCOHADA équilibrées, passerelle Mobile Money.
- **Hors-ligne** : les ventes sont mises en file (IndexedDB) avec un `clientId` unique (idempotent) puis synchronisées ; service worker pour le shell.
- **Scan** caméra via `BarcodeDetector` (Chrome Android).

## Fonctions serveur (`functions/dmp-api`)
Toutes les écritures passent par une seule fonction Appwrite ; **aucune table n'accorde d'écriture aux clients** (lecture seule pour l'équipe du commerçant). La fonction identifie l'appelant via l'en-tête posé par Appwrite, vérifie qu'il est membre confirmé du tenant, puis contrôle son rôle.

| Action | Rôle min. | Ce que fait le serveur |
|---|---|---|
| `checkout` | caissier | Relit prix et stock en base, refuse stock insuffisant / remise non autorisée, vérifie plafond de crédit et lien QR, écrit vente + mouvements + écritures SYSCOHADA, applique crédit et points. Idempotent. |
| `entity.save` | manager (client : caissier) | Produits, clients, fournisseurs ; champs serveur (crédit, points) non modifiables. |
| `stock.adjust` | manager | Inventaire par mouvement d'écart. |
| `credit.repay` | caissier | Remboursement de crédit + écritures. |
| `po.create/cancel` | manager | Bon de commande (prix HT, produits et fournisseur du commerce vérifiés), annulation avant toute réception. |
| `po.receive` | manager | Réception totale ou partielle : mouvements de stock + coût moyen pondéré. Idempotent par `receiptId`. |
| `invoice.supplier.create` | manager | Facture sur les quantités reçues non facturées (TVA incluse) ; écritures 601 + 4452 / 401. Idempotent par `invoiceId`. |
| `invoice.supplier.pay` | manager | Règlement total ou partiel (espèces, Wave, Orange, banque), plafonné au reste dû ; écritures 401 / trésorerie. Idempotent par `paymentId`. |
| `invoice.customer.fromSale` | manager | Facture-document à partir d'une vente (aucune nouvelle écriture comptable : la vente les a déjà passées). Une seule par vente. |
| `invoice.customer.create` | manager | Facture libre (prestation, client professionnel) : prix HT + TVA de la boutique ; écritures 411 / 701 / 4431. Idempotent par `invoiceId`. |
| `invoice.customer.pay` | manager | Encaissement total ou partiel ; pour une vente à crédit, le crédit du client baisse d'autant (plafonné au crédit restant). Idempotent par `paymentId`. |
| `shop.save` | owner | Fiche boutique (nom, adresse, NINEA/RCCM, TVA) utilisée en en-tête des documents. |
| `tenant.init` / `shop.create` | owner | Première boutique (idempotente) / nouvelle boutique (20 max). |
| `staff.create` | owner | Compte employé : identifiant (ou e-mail) + mot de passe initial, rôle (gérant, caissier, magasinier, comptable = préréglages), **accès par module** (Caisse, Clients, Stock, Achats, Factures, Compta, Rapports) modifiables, boutiques affectées. Rollback complet si une étape échoue. |
| `staff.update` / `staff.resetPassword` | owner | Rôle, boutiques, désactivation (le compte ne peut plus se connecter) ; nouveau mot de passe. Limités aux employés de son commerce. |
| `stock.transfer` | manager (accès aux deux boutiques) | Transfert immédiat entre boutiques : sortie + entrée de stock, produit de destination retrouvé par origine/code-barres ou créé. Idempotent, reprise sûre. |
| `payments.settings.save/get` | owner / caissier | Modèles de lien Wave / Orange Business. |
| `payment_link.create/confirm/cancel/status` | caissier | Lien de paiement, QR, confirmation. |

## Boutiques et employés
- Un commerce (Team Appwrite) peut avoir plusieurs boutiques. **Chaque appel serveur vérifie que la boutique existe dans le commerce de l'appelant et que l'employé y est affecté** (le propriétaire accède à toutes). Un employé désactivé perd l'accès immédiatement.
- Connexion des employés : l'identifiant (sans `@`) est complété en `identifiant@staff.invalid`. `.invalid` est un domaine réservé (RFC 2606) : aucun e-mail de récupération ne peut partir vers un tiers. Test réel : Appwrite accepte ce format. Le propriétaire réinitialise les mots de passe (pas de « mot de passe oublié » pour ces comptes).
- Le catalogue, le stock, les caisses et la comptabilité sont **propres à chaque boutique**. Un sélecteur de boutique apparaît pour qui en a plusieurs.
- **Isolation des lectures par boutique et par rôle.** Chaque ligne reçoit à sa création la liste des rôles autorisés à la lire (`functions/dmp-api/src/permissions.ts`) : le propriétaire lit tout ; les employés lisent via des **étiquettes** que le serveur pose sur leur compte (`s<boutique>` = affecté à la boutique, `g<boutique>` = gérant de la boutique). Caissier : produits, stock, clients, ventes, liens de paiement de **sa** boutique. Gérant : en plus fournisseurs, commandes, factures, compta, journal d'audit de **sa** boutique. Transferts : gérants des deux boutiques. Abonnement et paiements d'abonnement : propriétaire seul. Réglages de plateforme : personne côté client. Les étiquettes sont recalculées à chaque changement de rôle, de boutiques ou d'état (un compte désactivé n'a plus aucune lecture). Un test vérifie que **toute table du schéma a une politique** (une nouvelle table sans politique fait échouer le test et la création de ses lignes : jamais de lecture ouverte par défaut).
- **Vérification réelle** : les tests simulent les permissions Appwrite en mémoire. Après déploiement, lancez `npm run verify:isolation` (clé API requise) : il crée une table et des comptes temporaires, lit « en tant que » chacun, puis nettoie. **Ce script n'a pas encore été exécuté.**
- **Articles (formule Business).** Réservé aux formules Business et Pro (Starter garde l'écran Stock actuel, sans historique de prix, sans photo ni fiche enrichie, et ne voit pas l'entrée Articles ; actions `article.*` refusées en 402). Écran « Articles » : catalogue paginé (20 par page, curseur Appwrite), recherche (désignation en plein texte, début de référence, code-barres exact), filtres actifs / archivés / catégorie, tri, liste ou grille, fiche détaillée avec marge indicative, alerte de vente à perte, historique des prix et stock issu du journal de mouvements ; création et modification (photo prise ou choisie dans la galerie, compressée à ≤ 800 px / ~300 Ko avant envoi), archivage/restauration, suppression seulement sans historique, inventaire. Les articles sont la table `products` étendue (prix de vente = `price`, prix d'achat = `cost`, archivé = `archived`, stock = somme de `stock_moves`) : aucun doublon de table, Stock/Caisse/Achats/Rapports continuent de fonctionner. Colonnes ajoutées : `description`, `unit`, `supplierId`, `imageFileId` ; table `price_history` ; bucket privé `articles` (photos lisibles par le propriétaire et les employés de la boutique, créées par la fonction uniquement) ; index plein texte sur le nom, index référence, catégorie. Écritures : `article.save/archive/delete/image` (validation serveur, unicité référence/code-barres par boutique, création idempotente, journal d'audit). Droits de **formule** centralisés dans `src/domain/features.ts` (distincts des rôles) : fiche enrichie, photo = Business ; variantes, multi-conditionnement, tarifs par client/quantité, lots, séries, catalogue multi-magasins, bundles et analyses de rentabilité sont listés comme verrouillés Pro (non développés). Les ventes figent prix et coût dans leur ligne : modifier un article ne change jamais une vente passée. La fonction `dmp-api` a besoin des droits `buckets.read`, `files.read`, `files.write`.
- **Articles Pro, phase 1 : quantités décimales et conditionnements.** Réservé à la formule Pro (compte à vie inclus). Chaque article a une *précision de quantité* (0 à 3 décimales) : le stock est toujours une somme d'**entiers** de sous-unités (1,5 kg = 1500 g), jamais de nombres à virgule. Conditionnements (`article_units`) : « 1 carton = 12 pièces », coefficient validé à la précision de l'article ; une vente de 2 cartons retire 24 pièces, la ligne de vente et le mouvement de stock gardent l'unité et la quantité vendues (`unit`, `unitQty`, `factor`). Les montants sont arrondis au franc par le même code que le serveur. S'appliquent à la caisse, l'inventaire, les achats (commande, réception, coût moyen), les transferts et le stock valorisé des rapports. Retour en Business : conditionnements et changement de précision refusés (402), mais la vente à l'unité de base, y compris au kilo, continue et rien n'est supprimé. Restent à faire (phases suivantes) : variantes, tarification, fournisseurs multiples/coûts, lots/séries, bundles, tableau de bord et alertes. Le prix d'un conditionnement est pour l'instant le prix de base × coefficient ; des tarifs propres viendront avec la phase tarification.
- **Articles Pro, phase 2 : variantes.** Réservé à la formule Pro. Un article peut être décliné (Taille, Couleur, Modèle, Format, Matière ou attribut libre, 5 au plus, 200 variantes par article). Chaque variante (`article_variants`) a son SKU, son code-barres, ses prix de vente et d'achat, son seuil, sa photo facultative et son statut actif/archivé ; son stock est la somme des mouvements portant son `variantId` (`stock_moves.variantId`) ; une même combinaison d'attributs n'existe qu'une fois par article ; SKU et codes-barres sont uniques dans la boutique, articles et variantes confondus. Un article décliné se vend, se compte (inventaire), se commande, se réceptionne (coût moyen pondéré **par variante**), se transfère (la variante est retrouvée ou copiée dans la boutique cible, stocks séparés) et se valorise **variante par variante** ; la caisse propose le choix de la variante (ruptures grisées) et le scan d'un code-barres de variante la sélectionne. Le prix et le coût de la variante sont figés dans la ligne de vente, avec son `variantId` et son libellé. Un article qui a du stock doit être compté à 0 avant d'être décliné. Pro → Business : lecture, **vente** et rapports continuent (la caisse ne s'arrête pas), création/modification/archivage/suppression refusés (402).
- **Articles Pro, phase 3 : tarification avancée.** Réservé à Pro. Trois types de tarifs (`article_price_rules`) par article ou par variante : *promotion* (dates de début et de fin), *prix par catégorie de clients* (gros, revendeur ; catégorie portée par la fiche client, attribuée par un gérant) et *prix par quantité* (palier), éventuellement propres à un conditionnement (prix du carton). Ordre d'application, identique dans l'appli et sur le serveur (`src/domain/pricing.ts`) : promotion en cours > catégorie de clients > palier de quantité > prix de base ; à rang égal : priorité saisie, règle propre à l'unité, règle réservée à une catégorie, plus grand palier, plus récente. Les tarifs sont propres à chaque boutique. Le prix appliqué, sa source et la règle (`priceSource`, `priceRuleId`, `basePrice`) sont **figés dans la ligne de vente**, évalués à la date de la vente (une vente saisie hors ligne pendant une promotion garde le prix promotionnel) ; modifier ou supprimer un tarif ne réécrit jamais une vente passée. Pro → Business : les tarifs sont conservés mais plus appliqués (prix de base), création/modification refusées (402).
- **Articles Pro, phase 4 : fournisseurs, coûts et valorisation.** Réservé à Pro. *Fournisseurs multiples* (`article_suppliers`, une fiche par article/variante/fournisseur) : référence, prix d'achat, délai, quantité minimale, frais en %, statut, dernier prix payé et date ; comparaison automatique (prix effectif avec frais, puis délai, puis minimum) avec « meilleure offre ». À la **réception** d'une commande : frais d'approvisionnement saisis (transport, douane…) répartis au prorata de la valeur de chaque ligne (somme exacte au franc), frais % du fournisseur ajoutés, **coût de revient** calculé puis valorisé selon la **méthode de la boutique** (une seule par boutique : coût moyen pondéré ou dernier prix d'achat ; choix par le propriétaire dans Réglages, journalisé, effectif pour les réceptions suivantes) ; chaque réception écrit une ligne d'**historique des coûts** (`article_cost_events` : prix payé, coût de revient, coût du stock avant/après, variation) et met à jour la fiche fournisseur. Fiche article : marge brute, **taux de marge** (sur le coût) et **taux de marque** (sur le prix). **Rentabilité** par article/variante et par catégorie sur 7/30/90 jours : CA hors TVA − coût figé à chaque vente, avec la part du CA dont le coût est connu (jamais de marge inventée). Les commandes proposent le prix négocié du fournisseur et alertent si la quantité est sous son minimum. Pro → Business : fiches et historique conservés ; plus de frais ni de choix de méthode (402) ; la méthode en place continue de s'appliquer (une seule méthode, aucun changement silencieux). Hors périmètre de cette phase : valorisation FIFO (elle viendra avec les lots), comptabilisation des frais d'approvisionnement.
- **Articles Pro, phase 5 : lots, péremption et numéros de série.** Réservé à Pro. Mode de suivi par article (aucun / lot / série), modifiable tant que l'article n'a aucun mouvement. *Lots* (`article_lots`) : numéro, péremption, coût ; stock par lot = somme des mouvements portant `lotId` ; la vente prélève en **FEFO** (péremption la plus proche d'abord), les lots bloqués sont ignorés, les lots périmés sont refusés ou autorisés selon la politique de la boutique (Réglages, propriétaire, journalisée) ; mise au rebut tracée avec motif ; alertes à 30 jours. *Séries* (`article_serials`) : un numéro = une unité = un mouvement ; statuts disponible/vendu/garantie/retourné/défectueux avec transitions contrôlées ; à la caisse, **les numéros sont attribués automatiquement** (unités disponibles les plus anciennes d'abord) — le caissier peut aussi scanner l'étiquette d'une unité précise ; verrou par id unique annulé en cas d'échec ; la vente fixe la garantie. La réception de commande saisit lots (n°, quantité, péremption) ou numéros ; coût de revient dans le lot/la série. Le coût de vente et la valorisation utilisent le coût du lot (équivalent FIFO puisque la vente est FEFO). Les transferts d'articles suivis entre boutiques sont décrits plus bas. Hors périmètre : FIFO global. Pro → Business : données conservées, usage désactivé (402).
- **Articles Pro, phase 6 : bundles virtuels.** Réservé à Pro, dans un **module « Bundles » dédié** (tuile Bundles : liste, création en une étape avec nom, prix, référence automatique et composition, disponibilité, coût et marge indicatifs, archivage, suppression) — le formulaire d'article n'en parle plus et le catalogue Articles ne liste pas les bundles. Un article de type *bundle* (`products.kind`) a son propre prix mais **aucun stock propre** : sa composition (`article_components`, 1 à 20 composants parmi **tous les articles du commerce** : simples, à variantes (une variante précise par composant), au kilo/litre (quantités décimales), suivis par lot ou par numéro de série) définit ce qui sort du stock à chaque vente — un mouvement de vente par composant, composition et coût figés dans la ligne de vente (l'historique ne bouge pas si la composition change). Disponibilité = min(⌊stock du composant ÷ quantité⌋), recalculée à l'affichage. Chaque composant passe par la même affectation qu'une ligne de vente : variante, **lots en FEFO** (lots périmés/bloqués exclus), **numéros de série attribués automatiquement** (vendus avec la référence de vente), stock cumulé avec les autres lignes de la vente. Refus serveur : stock insuffisant (composant nommé), bundle sans composants, composant archivé, bundle imbriqué ; un *kit physique* n'accepte pas d'article suivi par lot/série (utiliser un bundle virtuel) ; un bundle ne se compte pas, ne se commande pas, ne se transfère pas, n'a ni variantes ni conditionnements ; un composant utilisé ou un bundle déjà vendu ne se supprime pas. Pro → Business : composition conservée en lecture, création/vente de bundles refusées (402). Le kit physique est décrit plus bas.
- **Articles Pro, phase 7 : tableau de bord et alertes.** Réservé à Pro (tuile « Tableau de bord »). Indicateurs calculés sur les données réelles de la boutique active : valeur du stock (lots à leur coût, bundles exclus), articles actifs, ruptures, stock bas, lots périmés / proches de la péremption (30 j), ventes à perte, bundles bloqués, et meilleurs articles sur 7/30/90 jours par chiffre d'affaires et par marge (coût figé à la vente, jamais de marge inventée). **Alertes du jour** persistées dans `article_alerts` : une ligne par (type, objet, jour) à identifiant déterministe → dédupliquées et traçables ; « Lu » enregistre qui et quand. Si l'historique de mouvements dépasse la borne de lecture, les chiffres de stock sont omis (`partial`) plutôt que faux. Pro → Business : alertes conservées, tableau de bord refusé (402). Limite : les alertes se calculent à l'ouverture du tableau de bord (pas de notification poussée ni de tâche planifiée).
- **Module Promotions (Business et Pro).** Tuile « Promotions » : liste filtrable (statut, période, article, catégorie, recherche nom/code), création/modification, détail avec conditions et **historique des utilisations**, onglet **Résultats**. *Types* : remise en %, remise en montant fixe (par unité), prix promotionnel ; *portées* : articles choisis, catégorie, toute la vente (avec **code promotionnel** obligatoire) ; conditions facultatives : quantité minimale, panier minimal, limite globale, limite par client, priorité. *Statuts* : brouillon → activée (« programmée » tant que le début est futur, « active » dans la période, « terminée » après la fin) ↔ suspendue, fin anticipée ; le statut effectif se recalcule à chaque vente avec la **date de la vente**. **Tout est calculé et vérifié par le serveur** (`checkout`, aperçu `promotions.preview` = même calcul sans rien écrire) : l'application n'applique jamais une promotion seule. Règles : une seule promotion par ligne (la plus avantageuse, puis priorité, puis la plus ancienne) ; jamais cumulée avec un prix de tarification spécial (Pro) ni une remise manuelle ; remise plafonnée à la ligne (aucun prix négatif) ; **marge minimale** de la boutique (Réglages) : promotion refusée à la création et ignorée à la caisse si le prix final passe sous coût × (1 + marge), sauf autorisation explicite ; limite globale **réservée atomiquement** par slot à identifiant unique (deux ventes simultanées ne dépassent jamais la limite) ; limite par client (client identifié exigé). Chaque utilisation (`promotion_usage`) est liée à la vente réelle (remise, base, montant net, lignes, caissier) ; la vente garde sa remise figée : modifier/terminer une promotion ne recalcule jamais une vente passée, une reprise réutilise la remise déjà figée, une promotion utilisée garde sa définition (on en crée une nouvelle) et ne se supprime pas. Tables : `promotions`, `promotion_items`, `promotion_usage` (+ `shops.minMarginPct`) ; `businessId` du cahier des charges = `tenantId`. Suivi : promotions par statut, utilisations, remises accordées et chiffre d'affaires des lignes en promotion **net de remise (jamais présenté comme un bénéfice)**. Formule Starter : aucune promotion appliquée, données conservées. Pas de Realtime : sans objet (les écrans se rafraîchissent à l'ouverture). Hors ligne : l'aperçu n'est pas disponible, les promotions sont appliquées par le serveur à la synchronisation (au moment de la vente).
- **Kit physique et ordres d'assemblage.** Réservé à Pro, dans le module Bundles : à la création, un bundle est *virtuel* (sans stock) ou un *kit* (`bundleMode = kit`, mode non modifiable). Un kit a son propre stock, alimenté par un **ordre d'assemblage** (`kit.assemble`, table `assembly_orders`) : les composants sortent du stock (mouvements `assembly_out`), les kits entrent (`assembly_in`), le coût du kit devient le coût moyen pondéré ; le **démontage** fait l'inverse. Ordre enregistré d'abord (« pending », composition figée) puis mouvements à identifiants fixes : une coupure se reprend sans rien doubler. Refus : composants insuffisants (nommés), quantité invalide, kit sans composants, archivé. La caisse vend un kit comme un article à stock propre (les composants ne bougent pas à la vente). Un kit ne se commande pas, ne se transfère pas (on l'assemble dans la boutique de destination), mais peut être compté en inventaire ; il ne se supprime plus une fois assemblé.
- **Transferts d'articles suivis.** Réservé à Pro. *Lots* : prélevés en FEFO (lots périmés ou bloqués exclus), recréés à l'identique (numéro, péremption, coût) dans la boutique de destination, retour possible vers l'origine. *Séries* : numéros choisis ou plus anciens disponibles, « transféré » à l'origine, « disponible » à destination (nouveau cycle si un numéro revient) ; réservation par identifiant unique (conflit avec une vente simultanée : tout est annulé). Un transfert avec articles suivis enregistre d'abord son plan (fiche `pending`, lots et numéros figés, colonne `transfers.status`) puis les mouvements ; une reprise complète sans doubler. Les conflits en destination (même lot avec une autre péremption, numéro déjà présent) sont refusés avant toute écriture.
- **Interface.** Charte noir + or (variables CSS dans `src/index.css`), logo et icônes générés par `node scripts/make-brand.cjs` (SVG, favicon, PNG 192/512, maskable, apple-touch). Accueil = tableau de bord (ventes du jour, tickets, alertes de stock, accès rapides selon les accès du compte), barre de navigation Accueil + 3 modules + « Plus », réglages en sections (Commerce, Boutiques, Équipe & accès, Paiements QR, Abonnement, Plateforme).
- **Accès du personnel.** Le propriétaire est le *gérant principal* (tous les accès, équipe, boutiques, abonnement). Il peut nommer d'autres gérants et cocher module par module ce que chaque employé peut faire ; la fonction vérifie le module à chaque action et les étiquettes de lecture suivent les modules. Seul le propriétaire gère l'équipe, les boutiques et l'abonnement. Compte propriétaire de la plateforme : accès **à vie** (statut `lifetime`, mises à jour incluses, aucune relance).
- **Limite restante** : la liste des membres de l'équipe (identifiants, rôles) reste visible de tous les membres du commerce (c'est le comportement des équipes Appwrite).

## Abonnements SaaS
- **Périodes** : Jour, Semaine, Mensuel, Trimestre, Annuel (durées fixes : 1, 7, 30, 90, 365 jours), achetables par multiples (jusqu'à 31 jours, 8 semaines, 12 mois, 4 trimestres, 3 ans).
- **Formules** (quotas boutiques / utilisateurs / produits) : Starter 1/2/200, Business 3/10/2 000, Pro 20/100/illimité. **Les tarifs par défaut sont des valeurs de départ à valider** (`src/domain/subscriptions.ts`) ; l'administrateur les modifie sans redéploiement (Réglages → Plateforme).
- **Essai gratuit** : 14 jours, formule Business, démarré à l'inscription.
- **Quotas appliqués côté serveur** : création de boutique, d'employé (le propriétaire compte ; un compte désactivé libère une place) et de produit (les produits archivés ne comptent pas). Modifier l'existant reste permis.
- **Expiration** : après l'échéance, délai de grâce (jour : 0, semaine : 1 jour, mensuel et plus : 3 jours ; essai : 0), puis **accès suspendu** : toute action d'écriture est refusée côté serveur (402) sauf le renouvellement, et l'interface affiche un écran de verrouillage à la place des pages (seul le propriétaire accède encore à Réglages → Abonnement). Les données sont conservées ; il n'y a pas de consultation en lecture seule dans l'application. Les ventes faites hors ligne pendant le verrou restent en attente et partent après renouvellement.
- **Paiement par liens Selar (sans API)** : un **produit Selar par formule** (3 liens : Starter, Business, Pro). Sur la page Selar, le client ouvre la liste « Choisir un abonnement » et choisit sa période (Chaque day, week, month, quarter ou year, aux prix du catalogue) puis paie. Dans l'application (Réglages → Abonnement), il choisit la formule et la période, touche « Payer sur Selar » (bouton + QR code du lien de la formule ; la consigne lui rappelle l'option exacte à sélectionner sur Selar), puis saisit la **référence de commande** reçue par e-mail et **l'e-mail utilisé**. **La plateforme vérifie dans son tableau de bord Selar** (commande trouvée, **option de période identique à celle demandée dans l'application**, montant exact, e-mail) **puis valide** ; aucune vérification automatique n'est possible sans API. Une référence ne sert qu'une fois sur toute la plateforme. Même formule encore active : la durée s'ajoute à l'échéance ; changement de formule : la nouvelle période démarre maintenant (le temps restant de l'ancienne n'est pas reporté). Validation idempotente. Les liens doivent être en https ; un domaine qui n'est pas `selar.co` / `selar.com` est signalé (pas refusé). **Si Selar renouvelle automatiquement l'abonnement, chaque renouvellement est un paiement que l'application ne voit pas** : la plateforme prolonge alors le commerce avec « Attribuer un abonnement ». Les paiements **en boutique** (clients qui paient leurs achats) restent des liens/QR Wave et Orange Business du commerçant : ils ne passent pas par Selar.
- **Accès à vie** : un commerce peut avoir un accès à vie (statut d'abonnement `lifetime`) : jamais d'échéance ni de relance, **aucune limite** de boutiques, d'utilisateurs ou de produits (hors plafond technique de 20 boutiques), toutes les fonctions présentes et futures (traité comme la formule la plus haute : aucune fonction future ne sera réservée à une formule payante sans l'inclure). Il est accordé **automatiquement au commerce créé par un compte administrateur de la plateforme** (`PLATFORM_ADMINS`) et **manuellement** par l'administrateur (Réglages > Plateforme > Accès à vie, retrait possible, tracé dans le journal d'audit). Un paiement, une attribution ou une demande de paiement ne le modifient jamais. Seule la plateforme peut l'accorder : le propriétaire d'un commerce ordinaire ne le peut pas.
- **Relances d'expiration (sans envoi automatique)** :
  - *Dans l'application* : un bandeau prévient le propriétaire **et les employés** (message adapté : le propriétaire est renvoyé vers Réglages → Abonnement, l'employé est invité à prévenir le propriétaire). Les paliers dépendent de la période : mensuel / trimestre / annuel à J-7 (information), J-3 (avertissement), J-1 (urgent) ; semaine à J-3, J-2, J-1 ; jour dans les dernières heures (12 h, 6 h, 2 h 30) ; un essai est relancé comme un mensuel. Les rappels d'information et d'avertissement se masquent pour la journée ; urgent, délai de grâce et accès suspendu restent affichés.
  - *Pour la plateforme* : Réglages → Plateforme → **Relances** liste les abonnements qui se terminent d'ici 7 / 14 / 30 / 90 jours ou sont déjà échus (essais compris), du plus urgent au moins urgent, avec le propriétaire, son téléphone, un **message déjà rédigé**, et les boutons WhatsApp (lien `wa.me`), e-mail (`mailto:`), Copier et « Marquer relancé » (date mémorisée). Un abonnement avec paiement en attente de validation est signalé pour ne pas relancer quelqu'un qui a déjà payé. Le lien WhatsApp exige un numéro avec indicatif ; pour un numéro local, saisissez l'indicatif par défaut (ex. 221), sinon l'application ne devine pas.
  - **Pas d'envoi automatique** : cela demande un service d'envoi (Appwrite Messaging avec un fournisseur SMTP/SMS configuré, ou l'API WhatsApp Business) et une fonction planifiée. Ce n'est pas branché ; la liste est limitée aux 100 échéances les plus proches.
- **Administrateur de la plateforme** : défini par la variable de la fonction `PLATFORM_ADMINS` (identifiants utilisateur séparés par des virgules). Inscrivez-vous dans l'application, copiez « Mon identifiant » (Réglages → Général), puis ajoutez la variable dans la console Appwrite (Functions → DMP API → Settings → Variables) et redéployez. Sans cela, personne ne peut valider les paiements.

## Rapports consolidés
Compta → **Rapports** (propriétaire : toutes les boutiques ; gérant : ses boutiques ; caissier : pas d'accès). Périodes : aujourd'hui, 7 jours, 30 jours, ce mois, mois dernier (92 jours maximum, **jours en heure UTC**). Contenu : chiffre d'affaires TTC / HT / TVA, nombre de ventes, panier moyen, **marge brute**, histogramme par jour, encaissements par mode (la monnaie rendue n'est pas comptée), détail par boutique, produits les plus vendus (regroupés par code-barres entre boutiques, sinon par nom), crédits clients ouverts, factures clients à encaisser, dettes fournisseurs, stock valorisé au coût moyen et nombre de produits en alerte. Export **PDF** partageable. Lecture seule : reste consultable quand l'abonnement est expiré.
- **Marge sans invention** : le coût d'achat est **figé sur chaque ligne de vente** au moment de la vente (une modification ultérieure du coût moyen ne réécrit pas l'historique). Un produit sans coût renseigné n'a pas de coût figé : la marge brute n'est alors **pas affichée** ; le rapport indique la part du chiffre d'affaires dont le coût est connu et une marge indicative sur cette part. Aucune marge de 100 % trompeuse.
- **Rien de faux en cas de volume** : lecture paginée avec bornes (20 000 ventes, 100 000 mouvements de stock par boutique). Si la borne des ventes est atteinte, le rapport est marqué « partiel » ; si celle du stock l'est, la valeur du stock et les alertes sont **omises** plutôt que fausses.
- **Date de vente bornée** : la date d'une vente (envoyée par le téléphone, vente hors ligne) est refusée si elle est dans le futur (> 10 min) ou de plus de 45 jours, pour qu'elle ne puisse fausser ni rapports ni comptabilité. Une vente hors ligne plus ancienne que 45 jours sera marquée « refusée » dans la file et demandera un traitement humain.
- **Correction liée** : le calcul du stock (serveur et application) lit désormais **tous** les mouvements par pages, au lieu de supposer qu'une requête de 5 000 lignes renvoie tout.
- **Limites** : calcul à la demande (pas de totaux pré-calculés) : lent sur de très gros volumes, d'où les bornes ; pas de comparaison avec la période précédente ni de rapport par vendeur ; pas de paramétrage du fuseau horaire.

## Paiement par QR code (Wave Business / Orange Business)
1. Le propriétaire colle dans *Réglages* le modèle de lien de son compte Business (https, avec `{amount}` et optionnellement `{ref}`). **Les formats exacts de lien ne sont pas codés en dur ni vérifiés ici** : ils viennent de votre compte Business.
2. À la caisse, choisir Wave ou Orange : le serveur crée un lien (réf. `DMP-XXXXXXXX`, validité réglable), l'appli le dessine en QR code.
3. Le client paie ; le caissier saisit l'**ID de transaction** reçu et valide. Un ID ne sert qu'une fois par commerçant, le lien expire, le montant doit correspondre exactement, un lien ne sert qu'à une vente, et tout est tracé dans `audit_log`.
4. **Limite actuelle** : la confirmation est manuelle (le serveur ne peut pas vérifier auprès de l'opérateur). Un webhook / une API opérateur doit la remplacer pour une garantie réelle (voir ROADMAP).

## État réel (v2.0.0-alpha)
Vérifié : typecheck, 386 tests (domaine + scénarios de la fonction, dont achats : réception partielle, reprise après plantage, double facturation, règlements sur un store en mémoire : isolation entre commerces, droits, idempotence, plafond de crédit, stock, liens QR), build du front et de la fonction ; base et 12 tables créées dans Appwrite.

**Non vérifié** : aucun appel réel à Appwrite depuis le code (fonction non déployée, adaptateur `appwrite-store.ts` et appels `createExecution` jamais exécutés), rien testé sur un téléphone Android.
**Pas encore fait** : PDF de la facture fournisseur, impression Bluetooth directe du ticket (le PDF se partage mais ne s'imprime pas encore sans passer par une appli d'impression), devis, avoirs, invitation d'employés par e-mail, vérification opérateur des paiements QR. Écarts connus : à la réception, si l'exécution plante après l'enregistrement de la commande mais avant la mise à jour du coût moyen, ce coût n'est pas recalculé à la reprise (le stock, lui, est complété) ; les achats n'ont pas de réception sans bon de commande ni de retour fournisseur ; la dette fournisseur est calculée à partir des factures (le champ `balance` n'est pas utilisé). Autres écarts : le règlement d'une facture issue d'une vente à crédit et la fonction `credit.repay` réduisent le même crédit client sans se synchroniser (si le crédit est remboursé par `credit.repay`, la facture reste « partielle ») ; pour un règlement de facture, une coupure entre la mise à jour de la facture et celle du crédit client peut laisser le crédit non décrémenté. Les transactions Appwrite supprimeraient ces fenêtres. Autre écart : si l'exécution plante entre la mise à jour du client et le passage de la vente à « paid », une reprise pourrait appliquer deux fois le crédit/points de cette vente.
